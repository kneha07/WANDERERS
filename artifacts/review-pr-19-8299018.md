### Findings

- **medium M1 - the boot path still fails, with a new message.** `start.js:11` sets up `backend/.venv` only. `start.js:123-124` then starts `server.js`, which uses `fields.js`. `pickPython` finds no root `.venv` and returns `python`. That Python has no pipeline packages, so the job fails with `ModuleNotFoundError`. The 9009 is fixed, but issue #18's user outcome is not. The PR body "Not tested" asks someone to "confirm the job starts". The job starts and then fails. Name this as a follow-up issue (for example: `start.js` sets `WANDERERS_PYTHON`, or installs `pipeline/requirements.txt`), or say it in the PR body.
- **medium M2 - the reason to leave `server.js` alone is stale on main.** The PR body says `server.js` serves only the older `/api/lookup` route (issue #9). On main, `server.js:20` `PY` also drives the star database: `server.js:56` `spawn(PY, ["-u", "pipeline/star_ml.py", key])` (PR #22). That lookup checks only `.venv/bin/python` and falls back to `python3`, so "learn this star" on Windows has the same 9009 bug. The deferral is named, which is good. The scope reason must be updated, and a follow-up issue filed.
- **low L1 - the Git Bash branch probably never matches.** A venv made by MSYS2 or Git Bash Python has `.venv/bin/python.exe`. `fs.existsSync` does not add `.exe`, so `.venv/bin/python` is not found on Windows. Harmless (falls through to `python`), but the PR body and comment claim a case that a real machine does not produce.
- **low L2 - three Python lookups, three rules.** `start.js:31-37` (`python3`, `python`, `py -3`, version check), `server.js:20` (`WANDERERS_PY`), `fields.js:25` (`WANDERERS_PYTHON`). PR #20 adds a fourth copy (`test/run-all.js:16`). Not in this ticket's scope; record it as debt.
- **low L3 - the fallback `python` can be the Store alias.** On a Windows machine without Python, `python` is the WindowsApps stub and exits 9009 again. The message is then the same as before. Acceptable; a clearer error is a follow-up.

### Honest done-state

The PR claims only what it does. It names both gaps it knows ("not run on real Windows", "server.js left alone"). I ran it on Windows and the claim "the job starts" holds. It does not claim that on-demand fields work end to end on Windows, and they do not (M1).

### Verdict

**PASS.** No high finding. M1 and M2 are scope gaps outside the issue's "Fix" text, but they must be filed as follow-up issues before #18 counts as "on-demand fields work on Windows".
